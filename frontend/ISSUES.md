## ✅ Исправлено (2026-08-13)

| # | Было | Как исправлено |
|---|---|---|
| B2 | 🔴 Мессенджер молча терял сообщения, отправленные вскоре после открытия чата (или сразу после предыдущего сообщения). Корневая причина подтверждена документально (пойман точный WS-фрейм-ответ сервера): `useEffect` в `ChatPage.jsx:128-133` слал `markRead()` на КАЖДОЕ изменение `messengerMessages`, а обработчик `case 'message_read'` в `useMessenger.js:80-85` при получении подтверждения (эхо приходит отправителю тоже) создавал новый объект/массив `messages` → эффект видел новую ссылку → слал `markRead()` заново → сервер снова отвечал `message_read` → бесконечный цикл. За ~1 секунду улетало 20+ WS-фреймов `message_read`, что выжигало серверный rate-limit (`websocket_router.py:51`, 10 событий/10с на соединение). Любое реальное сообщение (`new_message`), отправленное в этом окне, получало от backend `{"status":"error","message":"Too many messages. Slow down."}` — фронт эту ошибку никак не показывал пользователю, сообщение просто исчезало. Комментарий у эффекта («backend upsert идемпотентен, повторные вызовы безвредны») был верен по идемпотентности, но не учитывал rate-limit — повтор дёшев для БД, но не бесплатен для WS-лимитера | В `ChatPage.jsx` добавлен `lastMarkedReadRef` — эффект пропускает повторный `markRead()`, если `lastGuid` для этого чата уже был отмечен, разрывая цикл вместо того чтобы полагаться на идемпотентность backend. Проверено живьём: 5 сообщений подряд без пауз (Enter → Enter → ...) — все 5 дошли и сохранились в БД, до фикса терялось стабильно 1 из 2. Не сделано: backend по-прежнему не логирует rate-limit-отказы (нашёл только по фрейму в `ws.onmessage`), и фронт всё ещё не показывает пользователю ошибку, если реальный rate-limit сработает по другой причине (не из-за этого цикла) |

## ✅ Проверено аудитом, проблем не найдено

Гонка обновления токена (`useAuth.js:70-83`) корректно дедуплицирована через синхронный `useRef`-промис-гвард. WS-reconnect (`useMessengerSocket.js`) закрывает старый сокет перед переподключением, каждый раз берёт свежий токен, backoff капается на 30с — дублей/утечки состояния сессии не найдено. Нет `console.log` токенов/пользовательских данных нигде в `src/`. Нет open-redirect поверхности — никакой код не читает `redirect`/`next`/`returnUrl` и не пишет `window.location.href =` из request-контролируемого ввода.
